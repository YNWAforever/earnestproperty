## Migration and rollout

`20261026170000_listing_estate_content.sql` uses the project’s existing versioned SQL workflow and is registered in `migration-versions.js`. It inserts twelve identities, completes/publishes the selected existing rows, and fills only missing authored address, text, image, English-name and SEO fields. It retains existing IDs, aliases (apart from the documented identity correction), authored content and explicit links.

The 58 backfill candidates must still be active, have null `estate_id`, and exactly match the reviewed listing number, title, address and source URL. The destination must match the expected slug, name and district and be published. Edited, inactive, explicitly linked and unrelated rows are skipped. Existing intake uses the canonical names/aliases; tests cover those future resolutions too.

**Apply the reviewed migration before rolling the public app to this commit.** The existing footer is statically built from `estatesWithPage`; deploying code before DB publication would expose temporary footer 404s. Cards, directory, detail queries and sitemap still respect the live DB publication gate. Comparison links now also require a published DB record.

This PR does not apply production migrations, merge, or deploy. The migration is idempotent in an owned in-memory PGlite rehearsal. Review target identity and the ordinary migration plan when applying it.
