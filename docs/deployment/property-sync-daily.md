# Daily 28hse collection operations

The checked-in workflow is inactive until repository variables are deliberately configured. It collects agent:540 at 02:17 Hong Kong time (18:17 UTC) on a standard Linux runner using Python 3.14 and Node 22. It does not run the application build, AI or a browser. Property.hk remains disabled.

## Activation prerequisites

1. Merge the reviewed implementation to the intended protected branch. Set `PROPERTY_SYNC_EXPECTED_BRANCH` to that exact branch (normally `main`). Branch validation applies to manual shadow runs too.
2. Confirm the repository is private and provision a private repository release with tag `property-sync-evidence`, restricted to authorized repository readers. GitHub release assets inherit repository access; this implementation intentionally rejects public repositories. Review the job's contents-write permission, protect workflow changes, and ensure Actions may upload release assets. Do not enable a public mirror of these files.
3. Verify production schema, versioned source policy, owned-field guards and authoritative baseline through the existing operator process. Approve parser `python-v2.1` there before setting `PROPERTY_SYNC_POLICY_APPROVED=python-v2.1`. The workflow never edits policy or schema. An old python-v2.0 historical receipt/payload cannot be rewritten or promoted as a new compatible baseline; perform the separately approved policy/baseline upgrade first.
4. Verify the existing managed Actions secret named `DATABASE_URL_UNPOOLED` is scoped to the intended database. Its value must never be copied into runbooks, outputs or repository variables. It is injected only into the apply step, after collection and immutable request upload finish.
5. Dispatch `shadow`, scope `agent:540`, from the approved branch. Inspect source access from the Linux runner, complete sale/rent terminal pagination, unique details, lifecycle counts and completeness gates. The live-access smoke test remains an operator gate; offline tests do not establish it. Shadow never advances the accepted database baseline.
6. Coordinate and record one handoff from the old MLS source schedule to this workflow. Disable only the old 28hse collection trigger using its own approved operations procedure. Never change CRM or WhatsApp drain schedules. Confirm no competing source collector remains active.
7. Set `PROPERTY_SYNC_DAILY_ENABLED=true`, then dispatch controlled `apply`. For a first compatible baseline only, explicitly select manual `bootstrap=true` after approving the database's corresponding starting state. Schedule runs never bootstrap automatically. All subsequent apply runs require a restored accepted full baseline. Confirm the full successful receipt, canonical differences and `accepted-<UTC-snapshot-stamp>-<run>-<attempt>.tar.gz` asset before considering activation complete.

Do not set any of these variables merely to test this code. If policy, migration, ownership, release access, baseline upgrade or schedule handoff is unresolved, remain in shadow and record the missing gate.

## Frozen replay and recovery

Every eligible request is pinned as `request-<run-id>-<attempt>.json` on the private evidence release before database access. On failure, inspect the immutable request and receipt. Dispatch `replay-shadow` with that exact asset name first, then `replay-apply` when the permanent error has been resolved through its approved process. Replay validates branch, agent scope and parser and reads the same bytes; it never collects again. The replay worker bounds transient retries to three attempts and bounded Retry-After delays. Outcome-unknown must reuse the same request identity and bytes. Never edit a request, snapshot timestamp or batch ID to force an import.

A missing release/request pin aborts before apply. If apply succeeded but accepted-baseline publication failed, the database receipt remains authoritative. Restore the missing evidence by replaying the same request and checking the receipt; do not silently use a failed request as a baseline. A replay older than the restored baseline must not replace it. The operator must investigate all failed jobs, including evidence upload failures; GitHub's failed workflow status is the notification mechanism, with no external messages sent.

The workflow selects only `accepted-<UTC-snapshot-stamp>-<run>-<attempt>.tar.gz` baseline assets by the captured snapshot chronology, using workflow run/attempt only to break timestamp ties. The stamp is UTC `YYYYMMDDTHHMMSSffffffZ`; an old workflow rerun with a newer collection therefore takes precedence over a newer workflow ID with older data. The selected archive timestamp must exactly match its payload before extraction, and its SHA-256 manifest, scope/parser and successful full receipt are revalidated. Legacy accepted filenames without timestamps fail closed and require operator reconciliation, never silent bootstrap. The workflow then restores `baselines/28hse/agent-540/baseline.json` before collecting. The database's transactional ingestion state and receipt are the authority; this runner copy only supports local completeness and difference checks. Do not infer acceptance from artifact creation, latest run ID, a dry-run receipt or a partial receipt. Bootstrap and recovery must be reconciled with the database by an operator.

## Evidence and retention

Ordinary restricted raw evidence is gzip-compressed and retained as an Actions artifact for 7 days. Compact request/receipt/baseline evidence, including each immutable `replays/<run>/attempts/<number>.json` receipt, is compressed separately for 90 days. A successful final retry does not discard preceding transient-failure receipts. Request files contain full source records and are sensitive even though called compact. Job summaries include only outcome and evidence references, never contacts or raw source records.

The latest accepted full baseline, all frozen request assets and failed-run `unresolved-*` bundles persist on the private evidence release independently of Actions artifact expiry. Release storage is not an independent database. Operators must retain the latest accepted compatible full baseline and all unresolved/replay-needed evidence until resolution; only after recording receipt reconciliation may they manually remove superseded/resolved assets. No automatic inventory/history deletion or release cleanup runs here. Ensure repository access, backup and storage quotas cover these retained assets. An upload/network failure can prevent durable retention, so a failed evidence step requires recovery within the ordinary artifact window.

## Rollback and cost limits

Set `PROPERTY_SYNC_DAILY_ENABLED=false` to stop scheduled runs and block manual applies. A running import is allowed to finish (`cancel-in-progress: false`); inspect its final receipt before changing the handoff. Shadow and replay-shadow remain available. Restore the old collector only after an explicit single-owner handoff; do not run both schedules. Disabling automation does not undo accepted property changes.

There is one daily run with a 60-minute job timeout, 2–3 second request delay, at most 100 index pages and three request attempts from the checked-in source configuration. Expected work is proportional to index pages plus distinct property details; no measured hosted-run time or monetary estimate is claimed yet. Record elapsed runner minutes, network request count, source throttling and compressed artifact/release sizes on the controlled smoke run. Review monthly Actions/storage consumption after activation; persistent unresolved assets can grow until reconciled. A timeout can leave import outcome unknown, requiring frozen replay rather than recollection.
