# Independent CMS review — tasks 2 and 3

Reviewed 2026-09-05 in `codex/audit-20260905`. Source review of the shared edit contract, server/client, both estate editing surfaces, article dialog, comparison component, atomic migration, recovery tests and disposable database runner. This report describes the reviewed pre-fix state; findings were sent directly to the implementation owners. No database, provider or production actions, and no routine test reruns were performed by this reviewer.

## Actionable findings

1. **P1 — Archive does not invalidate draft-only publication.** `neon/migrations/20260905110000_cms_atomic_mutations.sql`, archive branch and publish checks (approximately lines 61–69, 133–146): save a first draft with null publication base, archive its resource, then publish that same draft with its unchanged identity/edit token/null base. Archive leaves the draft active and current publication remains null, so all publish checks still pass and the archived resource becomes public. Retire/invalidate outstanding drafts inside the archive transaction; verify both serialized replay and archive/first-publish races. The existing DB race test starts with a publication and therefore misses this case.

2. **P1 — An older actor draft resurfaces after publishing a restore.** Restore inserts a new draft without retiring the previous actor draft (`cms_atomic_mutations.sql`, restore branch); `src/lib/neon/admin-cms.server.ts` selects the newest remaining actor draft before publication. Example: publication v1, actor draft v2, restored draft v3; publish v3 then reopen. v2 becomes the edit payload again with base v1, instead of publication v3, and subsequent saves conflict. Retire superseded working drafts while preserving private immutable history. Verify restore → publish → reopen → edit/save, including two actors. Do not change private drafts into globally readable history merely to hide them from active selection.

3. **P1 — Nullable legacy estate arrays make full-record publication fail.** The estate projector calls `jsonb_array_elements_text(COALESCE(payload->'facilities', '[]'::jsonb))` and the same for aliases (migration lines 79 and 81). Both real estate columns permit SQL NULL. Full live reads and reconciliation produce JSON null for those fields, which COALESCE does not replace, and array extraction raises a scalar error. An unrelated title edit on such a legacy estate cannot publish. Handle JSON null explicitly while preserving the intended null/empty-array semantics. Add an actual estate projection case with null facilities and aliases to the disposable suite; its publication cases currently exercise articles only.

4. **P2 — Successful stale loads overwrite the active CMS dialog.** `src/routes/admin.cms.tsx:425` and `:552`: `loadEstateRevisions` / `loadArticleRevisions` increment a sequence and guard only failure messages. After their awaited read they set payload/edit identity without checking the sequence. Resolve requests for A then B out of order, or close/create a new editor before A resolves: A replaces B or reopens the closed dialog. Guard the success path before every hydration update and test out-of-order successful reads for both resources.

5. **P2 — Slow Save discards newer text typed in the CMS dialog.** `src/routes/admin.cms.tsx:468` and `:587`: success handlers replace editor state with the submission-time `editingEstate` / `editingArticle` closure. Inputs remain editable while Save is pending, so newer typing is silently removed on success. Use a functional identity-only update that preserves current input (and respects editor identity/close state), while retaining the submitted server snapshot separately as the reviewed state. A delayed-save test should prove newer text remains visible and cannot publish until saved.

## Positive findings and acceptance limits

The reviewed server resolves full actor-owned drafts by resource ID, separates original base from current publication, supports explicit manager/admin draft review, and does not use the capped history/list for current-publication recovery. Both publishing handlers send the reviewed revision and persisted identity/token rather than implicitly saving again. The dedicated estate serializer overlays changed fields onto the complete original payload. Comparison preserves a copyable local snapshot without rebasing it.

The SQL uses one shared resource advisory lock before reads, unique versions/current publication, checks active staff roles and edit identity/token, and commits projection/revision/audit in one function call. Historical revision immutability and rollback structure are appropriate by inspection. These observations are not evidence of executed PostgreSQL concurrency semantics: no approved disposable database was available and this reviewer did not run the SQL. Existing injected tests cannot establish migration compatibility, transactional races, or deployed role/browser behavior.

Legacy reconciliation is opt-in and documented, not executed. It skips resources once any revision exists, so approved reconciliation must precede enabling edits; otherwise original legacy live snapshots can remain permanently absent from history. Record dry-run counts and preserve visibility on an approved disposable branch before application rollout. Also retain the real-schema migration and authenticated browser acceptance gates; the runner's minimal fixture schema alone does not establish either. Video/FAQ lifecycle and upload work remain separately owned task 3B scope.
