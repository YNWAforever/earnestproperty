# Independent Task7 pagination review

2026-09-05; audit-20260905 / codex/audit-20260905. Reviewed admin-pagination types/query/server, authenticated server-function boundary, leads/WhatsApp/CMS callers, and existing fixture tests. No source edits or provider calls; only this report was written.

## Findings

1. **P2: Existing message status updates never reach an open thread.** `src/lib/neon/admin-pagination-query.ts:41` uses immutable `m.created_at` for message cursors; newer reads apply a strict `(page_at,id) > cursor` boundary. `src/routes/admin.whatsapp.tsx:297` simultaneously requests detail with `includeMessages:false`, then only merges the newer rows. An already visible unknown/queued message later changed to accepted (or with a cleared error) never qualifies. Late history records inserted behind the newest boundary can also remain unseen. Reproduced without providers using the real query builder plus merge helper: an accepted database record at the saved cursor produced no incoming rows and the visible row remained unknown. Use a bounded refresh of the latest window plus incremental new rows, or a separately ordered mutation cursor with suitable update timestamps; preserve previously loaded history and drafts. Cover status reconciliation and late insert explicitly.

2. **P2: Saving from a later inbox page silently returns to that page on polling, and stale saves overwrite pagination metadata.** `src/routes/admin.whatsapp.tsx:540` fetches page one and resets `listCursor` state, but does not reset `listCursorRef.current`. The default refresh at line221 still uses that prior cursor, so the next 30-second poll restores the old page after the save visibly reset it. The setters for cursor/next cursor/total also run before the `listRequestId` check, permitting a save response superseded by a new search to overwrite that search's pagination token and total. Move all response state/ref changes inside the same request guard and atomically set both cursor state and cursor ref.

3. **P2: Mutable ordering skips unseen rows between pages.** `src/lib/neon/admin-pagination-query.ts:39,45` orders conversations and several CMS resources by updated_at, then uses a strict older-than cursor. A row on the next page that receives an update after page one moves ahead of the cursor and can no longer be reached by continuing the traversal. The current static equal-time fixtures do not cover this. Concrete ordering example: page one returns times 4,3; unseen time2 changes to5; next page less than3 returns time1 and misses that row. Use stable traversal keys or an explicit snapshot/traversal strategy, and test a mutation between page reads. A normal latest-first live inbox may intentionally reorder, but that limitation must not be represented as stable exhaustive pagination.

4. **P2: FAQ scope choices are derived only from the current page.** `src/routes/admin.cms.tsx:358` builds `faqScopes` from `data.faqs`, which now contains at most50 paginated rows; the selector at line1435 renders only those values. A scope present exclusively beyond the first page cannot be selected directly, and choosing one scope removes other scope options from the filtered response. Fetch a separate bounded/full distinct scope inventory independent of the row cursor and selected scope. This is a full-dataset filter regression from adopting pagination.

## Verified safeguards and limitations

- CRM actor predicates precede filters, cursor paging and total count. Messages join their parent conversation and enforce assigned staff for agent roles. Manager/admin scope is explicitly broad. Query parameters bind client filters; fixed resource mapping prevents arbitrary table selection. Cursor binding includes actor/scope/resource/filters, so tokens cannot cross those contexts.
- Timestamp cursors preserve six fractional digits, and UUID ties are ordered in SQL. Existing `node --test src/lib/neon/admin-pagination.test.mjs`: **10 passed, 0 failed**. This includes100,000 equal-time message identities, static pagination, authorization and injection fixtures. It does not cover mutable ordering or status mutation polling.
- Detail/message request epochs and selected-ID guards handle most stale successful responses. Older fetches pause background detail polls and merge by ID. Draft dictionaries survive selection changes. Incremental polls fetch at most50 rows each; catch-up continues over future polls, rather than immediately draining a backlog.
- No UI caller for the new contacts resource was found. The server resource is scoped, but this review cannot establish a completed full-contact selector workflow from that endpoint alone.
- CMS refresh success is sequenced, but its effect catch sets errors outside the sequence guard; stale failed requests can still show an error after a newer success. CMS paging buttons also invoke an async refresh without a rejection handler. These are smaller resilience concerns for follow-up.
- Root's approved database harness evidence was inspected, but no database command was run in this review. This review does not claim browser timing, authenticated interaction, or production acceptance.
