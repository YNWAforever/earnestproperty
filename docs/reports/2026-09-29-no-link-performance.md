# No-link inbox performance and action coverage (T14)

## Scope and reproducibility

All results below are synthetic local PGlite WASM on Windows, Node 24.18.0, with one database connection. The fixture creates one enquiry and portal reference per conversation, 95% visible to the test agent, and 20 or 200 messages per conversation. Permission functions are simplified fixture stubs. No production traffic, Neon multi-session load, provider call, or customer data was used. Run `node scripts/no-link-performance-fixture.mjs --conversations 10000 --messages 200 --readers 10 --runs 5 --out <path>`; allowed dimensions are bounded in the script. JSON artifacts beside this report record hardware, dataset, parameters, samples, payload and representative `EXPLAIN (ANALYZE, FORMAT JSON)` plans. One warm-up precedes each five-run measurement.

All displayed reads execute **one SQL statement** and return the exact visible total, not an estimated count. PGlite queues ten overlapping reads on one connection, so the 10-reader figures indicate local serialization, not Neon throughput. Percentiles use five samples for one reader and 50 samples for ten readers; they are directional, not a production service level objective. A separate analyzed 10k/200/1 baseline run measured p50/p95 394/472 ms versus optimized 80/141 ms. Both returned 9,500 visible conversations and the same 14,639-byte page.

## Measured change

The baseline query built all conversation details twice, once for count and once for the page. In the analyzed 10k/200 fixture, it visited 19,000 latest-message rows, 39,000 inquiry rows and 19,000 reference rows. The optimized unfiltered inbox pages authorized conversation IDs first, then reads details for at most 21 page rows; count still scans the full authorized scope. The corresponding observed visits were 21 message, 63 inquiry and 21 reference rows. Conversations were visited 19,021 times for count, page selection and page details. Filtered/search inbox queries keep their existing logic and exact total. A PGlite regression compares unfiltered, explicit `all`, and `open` results, including row details, cursor pages and private-row denial. No cache or guessed total was introduced.

This is a measured local improvement only. Need Neon `EXPLAIN (ANALYZE, BUFFERS)` on an isolated, representative branch and multiple real connections before adopting a performance target. Receipt persistence latency, worker queue lag, provider latency, UI data freshness, and viewport 360/390/768/1280 with keyboard, IME, dialog focus and soft keyboard remain **VERIFICATION_BLOCKED** without isolated app/role fixtures. No production blind-click or load test was run.

## Action inventory and coverage denominator

`2026-09-29-no-link-action-results.csv` is generated by `python scripts/no-link-action-reconcile.py <verified audit 03_Action_Inventory.csv> <output.csv>`. It preserves every source ID and the audit actor, conditions, handler, destination, effect, finding and test IDs. It contains 1,261 source-control occurrences, 15 workflow functions, one proposed action, and 13 new dynamic/deep-link/menu candidates: **1,290 records**. The script asserts the original source denominator and unique IDs. Exact duplicate signatures are marked as equivalence *candidates*; wrappers and shared callers remain individually counted until a rendered actor/state trace proves equivalence. Source code alone does not establish a distinct business action. Original 03/03b and defect probes stay immutable in the verified audit package.

The old audit recorded 3 PASS source controls, 805 BLOCKED and 453 NOT_TESTED source controls; those PASS results belong to baseline `b1263bc`, not this branch. Current rendered execution is **0/1,261** source occurrences, with 811/1,290 `BLOCKED_EXTERNAL` and 479/1,290 `NOT_TESTED` across all record kinds; current execution coverage is 0/1,290 and observed pass rate is undefined. Local Node/Bun/PGlite assertions in the task ledger are separate evidence and do not silently promote a rendered control to PASS. No N/A exclusion was applied. The CSV retains row-level blocker and readback. Permitted, direct denied, invalid, cancel, duplicate, stale, timeout, refresh, and next-actor proof for high-risk rendered actions remains in the denominator. Full source-to-render reconciliation requires an isolated app with authorized manager/agent sessions and synthetic data; provider outcomes need separate receipts.
