# SEO & Redirect Plan

P8 handoff doc. Describes the site's actual current SEO surface — canonical/meta
strategy, sitemap composition, structured data, robots rules, and every redirect
rule that ships to production — as implemented, not as originally briefed.
Written against `main` at the point all of P0–P7 had merged (2026-08-31).

## Canonical & meta strategy

- `src/content/seo.ts` exports `canonicalLink(path)` (bare-path canonical, no
  query string) and a `seo({ title, description, path, ogImage?, noindex? })`
  combinator that mirrors title/description into `og:title`/`og:description`
  and adds the canonical link in one call. Added in P7a; only migrated the 3
  routes that were still hand-rolling a raw canonical
  (`castle-peak-road.index.tsx`, `castle-peak-road.$segment.tsx`,
  `district.tsuen-wan.tsx`) — the ~40 other working routes that already had a
  correct, hand-written `head()` were deliberately left alone (low value, real
  regression risk for a wide mechanical migration).
- `district.sham-tseng.tsx` uses `canonicalLink()` directly, not `seo()` — its
  `og:title`/`og:description` genuinely differ from its `<title>`/meta
  description pair, which `seo()`'s 1:1 mirroring can't express.
- `/transactions` and `/estate-reviews` self-noindex
  (`{ name: "robots", content: "noindex,follow" }`) whenever their filtered
  result set is empty — both render a graceful empty state rather than a 404,
  but an indexed empty page is a soft-404 risk. Self-heals the moment real
  rows land, no redeploy needed.
- `/district/tsuen-wan` is explicitly `noindex: true` — orphaned (no
  nav/sitemap entry, client pruned 荃灣 from district navigation) but was
  previously indexable. This is a content/IA decision (whether to fully
  reinstate or retire the URL) that P7a's SEO-hygiene pass deliberately did
  not make; the page still resolves for anyone with an existing external
  link, it just doesn't invite new crawl traffic.
- Structured data: `organizationSchema()` (`src/lib/schema.ts`) renders
  sitewide via `__root.tsx`'s `RootComponent()`, gated by the same
  `showSiteChrome` public/admin split `SiteHeader`/`SiteFooter` use (moved
  off the homepage-only placement it had before P7a). Per-page JSON-LD
  (`BreadcrumbList`, `FAQPage`, `ItemList`, `VideoObject`) stays scoped to the
  routes that have that real content, capped to visible/verified data only
  (no structured data for content that isn't actually rendered).

## Sitemap (`src/routes/sitemap[.]xml.ts` → `/sitemap.xml`)

Built from three sources, deduplicated:
- **Static paths**: home, listings, castle-peak-road hub + all 3 segments,
  sham-tseng district, blog list, about, contact, legal pages (privacy/
  disclaimer/terms), mortgage, agents, videos, every `estateSeo` entry
  (published estates only), every `blogArticles` entry.
- **Conditional paths**: `/transactions` and `/estate-reviews` only appear
  once a live query confirms they have real rows (see noindex note above) —
  same self-healing mechanism, applied at the sitemap level too.
- **Agent paths**: every public agent profile with a `public_slug`, fetched
  live via `listPublicAgentProfiles()`. A DB failure here degrades to zero
  agent URLs (logged loudly, not silently swallowed) rather than failing the
  whole sitemap.

`lastmod`: estate and article URLs get a real per-page date from
`fetchSitemapTimestamps()` (both tables' `updated_at`, already written by the
admin CMS's publish/archive paths). Every other URL — home, district hubs,
corridor pages, legal pages, etc. — has no tracked per-page revision history,
so they share one honest "sitemap generated at" timestamp rather than a
fabricated per-page value.

`/district/ting-kau` is explicitly filtered out of every path list (it 301s,
see below — listing a redirecting URL in the sitemap wastes crawl budget and
sends mixed signals).

## `robots.txt`

```
User-agent: *
Allow: /
Disallow: /admin
Disallow: /auth
Disallow: /account

Sitemap: https://earnestproperty.vercel.app/sitemap.xml
```

Added `Disallow: /admin`, `/auth`, `/account` in P7a — the file had zero
disallow rules before that, meaning staff/auth surfaces were technically
crawlable (never indexed in practice, since nothing links to them publicly,
but not something a `robots.txt` should be silent on for an app with a real
staff CMS/CRM behind it).

## Redirects (`vercel.ts`)

Two sources, concatenated into one `redirects` array at build time:

### 1. Bulk legacy redirects — `src/generated/old-site-redirects.json`

**Currently empty (`[]`).** This file is meant to be generated by
`npm run migration:redirects -- artifacts/old-site-migration/RUN_ID`, which
reads a real crawl-and-parse run of the *old* production site
(`scripts/old-site-migration/discover.mjs` → `crawl.mjs` → the redirect
generator) and maps each legacy `property-detail/:oldId.html` URL to its
matching `/property/:listingNo` on the new site via `buildMatchKey()`'s
canonical join. **That crawl-and-generate step has not been run in this
environment** — there is no `artifacts/old-site-migration/` output checked
in, and this session had no access to the live legacy site to produce one.
**Practical effect**: every individual old listing-detail URL currently falls
through to the generic catch-all below (`/listings`, not the specific
matching listing) instead of getting a precise 301. This is the single
highest-value pre-launch SEO action still outstanding — running the
migration pipeline against the real old site would recover per-listing link
equity that today all collapses to one generic redirect target.
