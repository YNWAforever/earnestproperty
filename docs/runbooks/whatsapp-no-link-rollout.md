# WhatsApp no-link release and rollback runbook

Status at code review: **LOCAL_IMPLEMENTATION_VERIFIED / VERIFICATION_BLOCKED**. This runbook is a future operator sequence. It is not approval to change production, send messages, migrate Neon, alter a provider number, or merge.

## Fixed boundaries

Ordinary 28Hse/PropertyHK customer messages enter through the signed Woztell company webhook and durable receipt. `off` and `observe` can persist and show triage but cannot assign, notify, reply, mint a tracking link, or turn historical receipts into active effects. The server gate requires the original receipt and event to have the same new activation, verified live provider identity, fresh timestamp, exact company Channel, and immutable canary staff cohort. The locking `wa_prepare_no_link_followup` SQL then rechecks current MLS/source scope, staff alias, existing conversation owner and provider mapping. An accepted provider request remains unknown until authoritative Folder/assignee readback; delivery and human reply require separate evidence.

Earlier immutable review decisions and reference snapshots are not repaired by this additive correction. Keep them in triage; use reviewed enquiry correction or separately authorized reconciliation. Replaying an old event must not create new effects.

The existing `EP_WA_ENQUIRY_MODE` (`off`/`observe`/`active`) and `EP_WA_NO_LINK_EFFECTS_ENABLED` default-off switch remain. New server-only canary settings also default to absent/off:

| Variable                             | Source and use                                                                                                                                                                                            |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `EP_WA_NO_LINK_CANARY_CHANNEL_ID`    | Exact already verified receiving company Channel; one channel only. Must equal `EP_WA_COMPANY_CHANNEL_ID`.                                                                                                |
| `EP_WA_NO_LINK_CANARY_ACTIVATION_ID` | New reviewed activation UUID, matching `EP_WA_ACTIVATION_ID`; never reuse an old generation for expanded scope.                                                                                           |
| `EP_WA_NO_LINK_CANARY_STAFF_IDS`     | Comma-separated local staff UUIDs from verified active staff/provider mapping; checked at capture and execution, snapshot in immutable event evidence. IDs are support config, not daily operator inputs. |

The setting names above are configuration only; this branch does not set them in any deployment. If any is missing, malformed or mismatched, no-link effects stay off. Changing a cohort or channel requires a new activation so earlier receipts cannot gain new effects. The durable receipt's `effects_eligible` remains false by design; its captured mode, activation, origin, provider identity and time are checked alongside the immutable event snapshot.

Staff offboarding also needs a reviewed no-link enquiry handover: `inquiries.enquiry_owner_staff_id` remains provider-coupled and is not bulk relabelled by the generic staff deactivation. Check outstanding enquiries for that staff member, preserve the original decision/forwarder snapshots, and reconcile the whole-thread provider assignee before confirming a new enquiry owner. The CRM lead assignment is the current owner for manually forwarded enquiries.

## Rollback without data loss

1. Stop **new no-link effects** by setting `EP_WA_NO_LINK_EFFECTS_ENABLED=false` and clearing the canary activation/cohort in an approved config change; stop canary worker execution if needed. Keep the durable signed receipt path and visible triage. Do not assume that stopping one no-link switch should disable unrelated already active service flows.
2. Preserve `whatsapp_inbound_receipts`, interpretations, enquiry roots, reference links, assignment requests, unknown outbound intents, tracked links and audit rows. Do not drop the nine additive migrations, bulk remap staff, reassign a whole existing chat, or replay old enquiries as fresh. Pending/unknown provider actions require authoritative provider readback and recorded reconciliation before any retry.
3. Revert to a compatible application version only after old/new reader checks. Verify incoming receipts continue to persist, triage is visible, current agent scopes still deny other customers' history, and optional tracking links remain functional. Any partially accepted provider assignment stays review/unknown until actual readback.
4. Record deployment SHA, config revision, activation ID, masked receipt/enquiry/request IDs, timestamps, exact rollback step, operator and next verification owner. Resume shadow before any later canary.

## Forwarded enquiry request recovery (2026-09-30)

The CRM form stores an actor-keyed request journal in the original tab session. On an uncertain save result, reopen the form or reload this same tab and use the frozen original payload with the existing request-id idempotent capture; do not edit it or start a new request. This is a local SQL capture/readback, not a provider-message resend. A successful result clears the journal. A normal cancel before submission clears an unsent draft; closing an unresolved form retains its journal. Pending dialog close and duplicate submit are blocked; route leave is allowed and cannot be reversed by its late callback.

If storage is unavailable before submission, no API call occurs. If a stored journal is malformed, preserve it and have an authorized support actor reconcile existing forwarded-enquiry/lead/audit rows before deciding whether to recover or retire that local draft. Do not blindly clear it and recreate the enquiry. Tab closure, a different device/browser, or manually clearing browser storage are outside the client recovery guarantee; the durable SQL request-id record remains authoritative. No support query or correction may bypass the current staff/lead scope.

The new browser CRM save/refresh/next-actor cases use a test-only session model. They do not close the real Auth/HTTP and isolated Neon multi-session gates.
